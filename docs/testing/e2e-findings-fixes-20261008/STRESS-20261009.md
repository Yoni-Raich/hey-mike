## Actual tool and model evidence

The successful GPT workflow turn has nine outer tool calls/results: one expected rejection, save, describe, and six runs. The 96 nested workflow steps are not 96 outer model calls. All six runs report 16 done steps, zero skipped steps, and eight exact captured read outputs. No explicit UI verify conditions were configured, so the runner correctly marks those steps unverified; the read outputs and separate eight-file device check are the functional oracle.

Across the successful workflow, GPT Settings, own-UI and recovered Claude Settings turns there are **51 outer calls and 51 terminal results**. The only unsuccessful tool result is the deliberately oversized plan. Exact prompts were checked against persisted drafts before Send and against the app trace afterwards.

Both engines actually completed the same Settings prompt. This is **one successful sample each**, in a shared QA chat with engine parking/switching and different warm histories, not a three-repeat controlled ranking. It does not establish that either engine is generally faster. The old 3.398 s own-UI read did not recur in this eight-read sample; without a matched old-build baseline it does not prove the idle-event change caused the difference.

The initial Sonnet attempt failed after roughly 12 seconds, before any tool call, with an OAuth refresh error. Its trace contains a failed turn and honest error reply. A later Sonnet attempt succeeded without changing credentials, signing in, killing another process or reinstalling. Record this as an intermittent authentication reliability finding; the suggested competing-refresh cause in the error is **not independently confirmed**.

The two fast bursts each dispatched 100 inputs in about 35 seconds. ADB process/transport overhead is included in that wall time; a 0.10 s requested gap is not proof of exactly 10 inputs per second. These are bounded repeated-navigation tests, not CPU/RAM saturation. The final closed-drawer and live-state checks do not prove every intermediate open/close animation completed.

Android reported 1,018/23,830 janky frames (4.272%) over the warmed reset intervals. Fast bursts reported 391/2,883 (13.562%) and 388/2,917 (13.302%). Retain this as a **performance finding under burst navigation**, not a crash or a threshold-defined release failure. Touch-to-next-draw is not full animation, GPU/display presentation, model time or end-to-end task completion. All 12,000 retained warmed frame rows still have OEM Flags=32, so strict per-frame percentiles/deadline misses remain unavailable, not zero.

## Harness limitations and mistakes

- New chat deliberately reuses a message-free chat, even when it has a persisted draft. The first orchestration attempt stopped before input/Send because the draft was not empty. The original draft was preserved; a known completed QA chat was opened before creating the next QA chat. This is a harness precondition finding, not a newly proven app defect.
- The first fast burst had no touch-probe rows because returning to the app through a normal intent had disabled the opt-in debug probe. Its timing is unavailable, not zero. The second burst explicitly enabled the probe and kept separate evidence; the first burst is not silently credited with that measurement.
- The health sampler initially had a wrong local Python import path and exited before sampling. It was corrected, with its error retained in the run notes; actual health coverage starts at the first recorded sample.
- Only the first model case used a fresh QA chat. Subsequent GPT/Claude turns reused that synthetic QA chat and its parked engine histories. This batch is not evidence for isolated per-case cold-start behavior.

Crash buffer is empty; pre/post exit history is identical. Expected Xiaomi FileUtils warnings remain; they are not labelled app crashes.

The main app process remained the same across **87 samples**, with no sampling errors. Main-process PSS was 154,307 KiB in the pre-snapshot and 172,637 KiB in the post-snapshot, a retained increase of 18,330 KiB (about 17.9 MiB). Periodic sampling peaked at 187,174 KiB. Eleven cooldown samples were roughly stable around 177,000 KiB; the final functional check occurred after 145 seconds of cooldown. These samples and snapshots have different times, so do not equate their values or present a single instantaneous number as a trend.

Retained memory after load is an **unresolved resource observation**, not proof of a leak. This batch created a QA chat, parked/switched engines and retained streamed/tool history. No heap dump, equal-state cache control, child-runtime memory accounting, long soak or memory saturation test was performed. A longer repeated equal-state load with main/child process accounting is still needed.
